# Limitations and troubleshooting

## Known limitations

- **The copy is taken from a powered-off VM.** Powered-off and powered-on VMs can be migrated; a powered-on VM is shut down by the migration tool right before the NFC lease is opened (after the OCI instance and volumes are prepared), which the operator confirms per VM in a pop-up. The shutdown is a guest OS shutdown through VMware Tools, with a hard power-off when Tools is not running or the guest has not stopped after `HELPER_GUEST_SHUTDOWN_TIMEOUT_S` (default 300 s). The VM is not powered on again. Suspended VMs and templates are not offered (resume and shut down, or power off, first). There is no live/CBT sync.
- **Encrypted VMs cannot be exported.** vSphere refuses `ExportVm` (the OVF/NFC export the migration tool uses) on a VM with VM encryption enabled (`opUnsupportedOnEncryptedVm`), and a Virtual TPM device can only exist on an encrypted VM - so this covers most Windows 11 VMs, which vSphere creates with a vTPM. The migration tool detects this (`config.keyId`, a `VirtualTPM` device, disk backings with a `keyId`), shows the VM as *encrypted* in the list and refuses the migration before anything is created in OCI. Decrypt the VM in vCenter first: power it off, remove the Virtual TPM device (Windows 11 keeps booting without it once installed; suspend BitLocker inside Windows beforehand, since the OCI instance's vTPM is a different TPM anyway and BitLocker would ask for the recovery key), set *Edit Settings > VM Options > Encryption > Encrypt VM* to *None* (for encrypted disks: pick a storage policy without encryption), then migrate. On OCI the instance still gets a vTPM when the source used Secure Boot (shielded instance, see below).
- **Sources: vCenter Server or a standalone ESXi host** (see [how-it-works.md](how-it-works.md)). The server (and whether to verify its TLS certificate) is entered on the login page; any reachable vCenter or ESXi endpoint works (`HELPER_VCENTER_HOST`, if set, is only a pre-filled default). Other hypervisors (Workstation/Fusion, Hyper-V, KVM) are not supported.
- **One availability domain.** Boot volumes cannot leave their AD, so target instances are created in the migration tool's AD. Deploy one migration tool VM per AD if needed.
- **Guest drivers.** The disk content is copied verbatim, with two post-copy fix-ups for Linux (this one and the network one below): RHEL/CentOS/Oracle Linux (and SUSE) build a *hostonly* initramfs that only contains VMware's storage drivers, which ends in the dracut emergency shell in OCI (`/dev/mapper/rhel-root does not exist`). Enabled by default (*Rebuild the Linux initramfs with virtio drivers after the copy* under *Advanced*), the migration tool mounts the copied boot volume (plain partitions or LVM; a separate `/boot` is taken from the guest's fstab, whether written as `UUID=`, `LABEL=`, `PARTUUID=`, `/dev/disk/by-*/...` as Ubuntu's installer does, `/dev/mapper/vg-lv` or `/dev/sdXN`) and runs the guest's own `dracut --force --no-hostonly --add-drivers "virtio ..."` in a chroot for every installed kernel whose initramfs lacks virtio modules; it also drops `/etc/dracut.conf.d/oci-virtio.conf` into the guest so later kernel updates keep the drivers. Only the OCI copy is modified. The step is skipped with a reason for Windows, LUKS-encrypted roots, btrfs, guests without dracut (Ubuntu/Debian include virtio anyway) and when the guest's volume group has the same name as one on the migration tool; a failure is reported in the job but does not fail the migration. Windows guests need the [Oracle VirtIO Drivers for Microsoft Windows](https://docs.oracle.com/en/operating-systems/oracle-linux/kvm-virtio/) installed before the export (the export page shows this as an *Important* note for Windows VMs), or use the *Maximum compatibility* preset (IDE + E1000) and install the drivers afterwards.
- **Secure Boot** on the source (`efiSecureBootEnabled`) is matched: the instance is launched as a *shielded instance* from a seed image whose capability schema declares `Compute.SecureBoot`. On VM shapes OCI only offers Secure Boot together with Measured Boot and a vTPM, so all three are enabled (a Windows guest therefore gets a vTPM it may not have had on vSphere; on bare metal, Linux gets Secure Boot alone). This needs an x86 shape (AMD E-series, Intel Standard3/Optimized3, or bare metal); Ampere A1/A2 shapes are refused up front. Shielded instances cannot be live-migrated by OCI. The guest must boot through a boot loader signed for the Microsoft UEFI CA (shim-based Linux distributions, Windows); a guest that booted with custom Secure Boot keys on vSphere will not start in OCI.
- **Snapshots** are consolidated by the export (the current disk state is copied); snapshot history is not migrated.
- **Network configuration.** The network interface has a different name in OCI (`ens3`, `enp0s5` or `eth0` instead of `ens192`, depending on the shape's PCI layout, virtio vs E1000 and the guest's own kernel arguments), so the VMware profile - bound to that name and usually to a static address - never comes up on its own. Enabled by default (*Configure the Linux network for OCI after the copy* under *Advanced: firmware and device model*), the migration tool fixes this on the copied boot volume in the same mount session as the initramfs step, without predicting the name: a NetworkManager keyfile profile of `type=ethernet` without `interface-name`/MAC (matches any Ethernet device, IPv4 DHCP, `autoconnect-priority=100`); on guests using the legacy `network.service` a one-shot systemd unit that creates `ifcfg-<name>` with DHCP for every physical NIC without a file on the first boot and then disables itself; a netplan drop-in (`match: name: "e*"`) or a systemd-networkd `[Match] Type=ether` drop-in where those are used; and `*persistent-net.rules` udev rules (which pin `eth0` to the VMware MAC) are disabled with a `.vcoci-bak` backup. OCI's DHCP always hands out the VNIC's address, also a fixed private IP chosen in the dialog. New files are SELinux-labelled with the guest's own `setfiles` (chroot), else with `setfattr`, else `/.autorelabel` is scheduled. Old profiles are left in place. Skipped with a reason for Windows (the VirtIO adapter uses DHCP), RHEL 6 style guests without systemd (udev rule only) and guests with none of these stacks; a failure is reported in the job but does not fail the migration. Only one VNIC is created.
- **Retries restart a disk from the beginning** because NFC downloads cannot be resumed; progress of already copied disks is kept. A job that fails *after* all disks were copied (attach or start rejected by OCI) offers **Retry finalize** in the job view, which re-runs only the attach/start step against the existing volumes.
- **Windows targets get no consistent device paths** (`/dev/oracleoci/oraclevdX` is a Linux feature; OCI rejects the attribute for Windows instances). Data disks show up in Windows in attachment order.
- **Data volumes stay attached as *read/write shareable*.** OCI only attaches data volumes to a running instance, so they are attached while the target still runs from the seed image and the migration tool takes a second, shareable attachment for the copy; the guest then boots with every disk present. The target's attachments keep the shareable flag afterwards (harmless as long as nothing else attaches the volume; detach and re-attach as plain read/write if you want the guard back). With *Maximum compatibility* (emulated attachments, which cannot be shared) the target is started first and the data disks are hot-plugged; with *start after migration* off it is soft-stopped again afterwards.
- **Concurrency** is bounded by the migration tool's 32 attachment slots (`HELPER_MAX_CONCURRENT_JOBS` defaults to 2, adjustable up to 16 on the *Setup* page; further jobs queue).
- **Migration tool restarts abort running jobs.** The export runs on the in-memory vCenter session of the user who started it; after a service restart such jobs are marked `FAILED` and must be cleaned up and restarted.
- **Seed image import time.** The first job for a new firmware/OS combination waits for a custom image import (minutes). Later jobs reuse the image.
- **Windows licensing** is honoured because the seed image is registered as Windows; OCI applies its own eligibility rules for `OCI_PROVIDED`.
- **Session idle timeout** (`HELPER_SESSION_TTL_S`, 8 h, adjustable on the *Setup* page) logs the browser out, but never interrupts a running migration.
- **Create OCI instance based on ISO relies on undocumented OCI behaviour.** The installer ISO is imported with `CreateImage` and `sourceImageType = VMDK` (the only documented types are `QCOW2` and `VMDK`); OCI recognises the ISO content and an instance launched from such an image boots the ISO as installation media with a blank boot volume of the requested size attached (after the installation the instance boots from the boot volume). This is tested behaviour, not documented. Should OCI change or withdraw it, the import fails on the `iso_image` step (the image enters `DELETED`); the type token is configurable (`HELPER_ISO_SOURCE_IMAGE_TYPE`) in case a dedicated ISO type appears. The ISO flow needs no vCenter: the web UI runs on an *anonymous* session (created automatically when the page is opened) that can create ISO jobs, see all jobs, open remote consoles and use the *Setup* page; only *Source VMs* and the VMware migration form require the vCenter login. Windows ISOs work, but Windows Setup has no virtio drivers, so the form pre-selects *Maximum compatibility* (IDE + E1000); install the VirtIO drivers afterwards. The migration tool moves no data for these jobs; they survive a service restart in the `INSTALLING` phase.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Any failed job | *Copy diagnostics* in the job view (`GET /api/jobs/{id}/diagnostics`) collects the job record, the error and the relevant service journal lines as text for a bug report. For OCI `InvalidParameter` errors, enable *Log OCI API requests* on the Setup page and retry. |
| Login fails with *cannot connect to vCenter* | From the migration tool VM: `curl -k https://<vcenter>/sdk`; check routing/VPN, NSG egress and the address/port typed on the login page. |
| Login fails with *the TLS certificate ... could not be verified* | *Verify the server certificate* is ticked but vCenter/ESXi uses its self-signed or VMCA certificate: untick it, or install the issuing CA in the VM's trust store (`update-ca-trust`). |
| Login fails with *invalid user name or password* | Use the vCenter SSO form (`user@vsphere.local` or `DOMAIN\user`); the account must be allowed to log in to vCenter. |
| VM list is empty / a VM is missing | vCenter RBAC: the account needs read access to the VM; templates are hidden. Click *Refresh* (the list is cached for 30 s per session). |
| `the availability domain must be the migration tool VM's` | Choose the migration tool VM's AD in the dialog. |
| Seed image stuck in `IMPORTING` | Object Storage policy / bucket; `HELPER_IMAGE_IMPORT_TIMEOUT_S`. |
| `seed image ... entered state DELETED` (import failed) | The error lists the import work request and its OCI-side errors/log. No entries at all usually means the import service could not read the placeholder: it creates a pre-authenticated request on the seed bucket as the migration tool, so the migration tool's policy needs `manage buckets ... where all {target.bucket.name = '<seed bucket>', request.permission = 'PAR_MANAGE'}` (stacks deployed before 0.3.1: re-apply the stack or add the statement by hand; the Audit log shows `CreatePar 404` from `Oracle-JavaSDK` during the import). |
| `ISO image ... entered state DELETED` with `InvalidParameter: Specified namespace or bucket for image import does not exist` | The bucket exists (the picker listed it); this is how OCI reports that the import service may not read it. Same mechanism as the seed import above: the service reads the ISO through a PAR it creates as the migration tool, so the policy needs `read buckets`, `read objects` and `manage buckets ... where request.permission = 'PAR_MANAGE'` on the bucket's compartment. Stacks deployed before the ISO feature only have the seed-bucket statement: re-apply the stack with the current `vc-oci-helper-stack.zip` (only the policy changes; make sure the policy scope covers the bucket's compartment) or add the three statements by hand. If the object exists and the policy is right, OCI may no longer accept an ISO behind the `VMDK` type (see *Known limitations*). |
| ISO instance does not boot the installer / shows no disk | Check *Launch options* in the job view against the ISO (UEFI vs BIOS; Secure Boot needs a signed boot loader). An installer without virtio drivers (Windows Setup) needs *Maximum compatibility* (IDE + E1000). |
| `target instance entered state TERMINATING` | OCI accepted the launch and failed it asynchronously; the job error now appends the reason from the instance's work request (needs `read work-requests`). DNS host names are unique per subnet: the migration tool checks the subnet's private IPs before launching and uses `name-2`, `name-3`, ... when the VM name is already taken. |
| `cannot open /dev/oracleoci/oraclevdX` / `cannot open /dev/sdX` | The service must run as root (the systemd unit does) and the migration tool VM must use consistent device naming (data volumes); check `lsblk` on the migration tool VM. |
| `boot volume attached to the migration tool VM but its disk was not found` | The boot volume was attached without a device path (OCI does not allow one) and no new whole disk of the boot volume size showed up in `/sys/block` within `HELPER_VOLUME_TIMEOUT_S`. Check `lsblk` on the migration tool and that nothing else attaches volumes to it at the same time. |
| *VM is encrypted* on the export page / `vSphere NotSupported: ... The operation is not supported on encrypted VM` | VM encryption (always the case with a Virtual TPM, i.e. most Windows 11 VMs). Decrypt in vCenter as described under *Known limitations* (remove the vTPM, *Encrypt VM: None*) and migrate again. |
| `NFC lease did not become ready` / `GET ... returned HTTP 4xx` | The account lacks `VirtualMachine.Provisioning.ExportOVF`; or the NFC URL host is unreachable from the migration tool (set `HELPER_NFC_HOST_OVERRIDE` only if lease URLs point at ESXi hosts you can reach). |
| Export throughput is low (~15-25 MB/s) | By default the disk stream is proxied by vCenter, which caps around that rate. Tick *Download the disks directly from the ESXi host* in the migration dialog (migration tool must reach the host shown there on TCP 443 and resolve its name). Also check the VPN/FastConnect bandwidth; a higher *Volume performance (VPU/GB)* in the same dialog raises the write ceiling of the target volumes, and *Decode and write on a separate thread* overlaps the download with inflate/`pwrite` (helps when the migration tool's CPU or the volume, not the network, is the bottleneck). Per disk the stream is a single TCP flow compressed by one ESXi thread, so multi-disk VMs are the only case where more parallelism would help. |
| `direct ESXi download requested but vCenter reports no host for the VM` | vCenter has no `runtime.host` for the VM (orphaned/inaccessible). Fix the VM's placement in vCenter or start the migration without the direct download option. |
| `invalid VMDK stream` / `bad magic` | Something other than a stream-optimized VMDK was returned (a login page or error body); check the lease URL host and proxies between the migration tool and vCenter. |
| Disk retried three times then `FAILED` | Persistent network trouble between the migration tool and vCenter/ESXi; check MTU on the VPN/FastConnect path. |
| Linux target stops in the dracut emergency shell (`dracut-initqueue timeout`, `/dev/mapper/<vg>-root does not exist`) | The initramfs has no virtio drivers. Check the *Initramfs fix-up* row in the job view: if it was skipped or failed (reason given; details in *Copy diagnostics*), power the source VM on, run `echo 'add_drivers+=" virtio virtio_pci virtio_ring virtio_blk virtio_scsi virtio_net "' > /etc/dracut.conf.d/oci-virtio.conf && dracut -f --regenerate-all`, shut it down and migrate again. |
| Linux target boots but has no network (`ip a` shows the NIC without an address) | Check the *Network fix-up* row in the job view: if it was skipped or failed (reason given; details in *Copy diagnostics*), open *Remote console* and configure DHCP on the new interface: NetworkManager `nmcli con add type ethernet con-name oci ifname '*' ipv4.method auto`; legacy network-scripts: create `/etc/sysconfig/network-scripts/ifcfg-<nic>` with `TYPE=Ethernet DEVICE=<nic> BOOTPROTO=dhcp ONBOOT=yes` and `systemctl restart network`. If the profile was written but NetworkManager ignores it, check `ausearch -m avc -ts recent` for an SELinux denial on the keyfile and run `restorecon -Rv /etc/NetworkManager`. |
| Target does not boot | Firmware mismatch (compare *Launch options* in the job view with the source), missing virtio drivers (see the row above; Windows: install the VirtIO drivers or try compatibility mode), or a BIOS guest whose disk uses GPT without a protective MBR. Open *Remote console* in the job view to watch the boot (VNC through the OCI console connection; the migration tool must reach `instance-console.<region>.oci.oraclecloud.com:443`). |
| *Remote console* stays at `Connection lost` / `4502` | The migration tool could not open the SSH tunnel to the console service: no route from the migration tool subnet to `instance-console.<region>.oci.oraclecloud.com:443` (Service Gateway with *All Services in Oracle Services Network*, or NAT gateway; test with `curl -v https://instance-console.<region>.oci.oraclecloud.com` from the migration tool), or the service host key did not match the fingerprint OCI reported (see the migration tool journal). A `foreign_connection` prompt means a console connection created outside the migration tool exists for the instance; replace it or delete it in the OCI console. |
| Job `FAILED` with resources left behind | Inspect in the OCI console (tags `vc-oci-job=<id>`), then *Clean up OCI resources* in the job view (`POST /api/jobs/{id}/cancel`). |
| Job `FAILED: migration tool restarted` | Expected after a service restart; clean up and start the migration again. |

## Manual end-to-end test procedure

1. Deploy the migration tool; confirm `/api/health`, log in to the web UI and check that the VM list matches the inventory.
2. Create a small Oracle Linux 9 test VM (UEFI, PVSCSI, vmxnet3, 20 GB thin) in vCenter, install, note its disk checksum (`sha256sum /dev/sda` from a live ISO) and power it off.
3. Click *Migrate* in the VM list, keep the defaults and start. Expected sequence in the job view: PROVISIONING (seed image on first run) -> EXPORTING with per-disk progress -> FINALIZING -> COMPLETED.
4. In OCI, confirm the instance has `firmware=UEFI_64`, paravirtualized boot/network, a 50 GB boot volume, and boots to the console login.
5. Repeat with a BIOS + LSI Logic + e1000 Windows Server VM choosing BYOL; confirm `launchOptions.firmware=BIOS`, `bootVolumeType=PARAVIRTUALIZED`, `networkType=PARAVIRTUALIZED` (the source device model does not matter; only *Maximum compatibility* yields IDE + E1000), `licensingConfigs=[WINDOWS/BRING_YOUR_OWN_LICENSE]` (the license type is chosen when the migration is set up; change it later in the OCI console if needed).
6. Test failure paths: power the VM on before the export starts (job fails with a clear message), cancel a job mid-copy (instance and volumes removed), log out while a job is copying (job completes; log in again to see it).
